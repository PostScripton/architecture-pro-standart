### Нефункциональные требования

| **№** | **Требование** |
| :-: | :- |
| 1 | Данные о ставках в системе кол-центра банка должны обновляться с той же частотой, что и кеш Rate Cache Service (унаследовано из предыдущего ADR) |
| 2 | Максимальная задержка доставки файла ставок партнёру --- не более 24 часов (ставки меняются не чаще одного раза в день, согласуется с бизнесом) |
| 3 | Передача файла осуществляется по защищённому каналу (SFTP = SSH + FTP, шифрование на уровне транспортного слоя) |
| 4 | Сбой выгрузки файла на SFTP не должен влиять на работу системы кол-центра банка и основной поток обработки заявок на депозиты |
| 5 | Все изменения реализуются в рамках существующих систем --- новый технологический компонент только один: SFTP-сервер |

### Решение

**Кол-центр банка.** Rate Cache Service уже синхронизирует ставки из АБС по расписанию и предоставляет API интернет-банку. Со стороны Rate Cache Service достаточно добавить публичный endpoint `/rates`. Система кол-центра реализует виджет отображения ставок, который обращается к этому endpoint. Никаких изменений в АБС не требуется.

**Партнёрский кол-центр.** Партнёр не может делать API-вызовы, но готов получать файлы через SFTP. На стороне банка разворачивается SFTP-сервер. Rate Cache Service дополняется scheduled job, который по расписанию читает текущие ставки из кеша, формирует файл (CSV) и кладёт его на SFTP-сервер. Партнёр самостоятельно забирает файл по договорённому расписанию.

#### Логика принятых решений

**Расширение Rate Cache Service вместо создания нового сервиса**

Rate Cache Service уже содержит актуальные ставки. Добавление нового endpoint и нового scheduled job --- это минимальное изменение существующего компонента. Введение отдельного сервиса создало бы лишнюю операционную нагрузку и дублирование логики.

**SFTP как единственный канал для партнёра**

Партнёрский кол-центр работает во внешней информационной системе и не готов принимать API-вызовы. SFTP --- стандартный протокол файлового обмена, поддерживается большинством корпоративных систем и защищён шифрованием на уровне SSH.

**Файловая доставка по расписанию вместо push-уведомлений**

Самый простой способ интеграции с внешней системой без требований к её API. Банк отвечает только за своевременную выкладку актуального файла. Партнёр сам контролирует момент загрузки.

### Альтернативы

**Прямой API-доступ системы кол-центра к АБС**

Система кол-центра напрямую запрашивает ставки из АБС. Отклонён --- АБС перегружена, прямые обращения из внешних систем создают риск деградации. Rate Cache Service уже решает эту проблему и существует именно для таких сценариев.

**Webhook от банка к партнёру при изменении ставок**

Банк сам инициирует уведомление при каждом изменении ставок. Отклонён --- партнёр не готов к приёму входящих API-вызовов.

**Предоставить партнёру прямой доступ к API Rate Cache Service**

Внешний партнёр получает учётные данные и обращается к внутреннему API банка. Отклонён --- требует открытия входящего сетевого доступа к внутренней инфраструктуре для внешней организации. Это нарушает политику периметровой безопасности. Кроме того, партнёр технически не готов к API-интеграции.

**Недостатки, ограничения, риски**

- **Задержка актуализации у партнёра.** При изменении ставок в АБС партнёр получит обновление только в следующем цикле выгрузки. Максимальный лаг определяется расписанием и должен быть согласован с бизнесом.
- **Нет подтверждения доставки от партнёра.** Банк не знает, забрал ли партнёр файл и успешно ли его обработал. Необходим операционный процесс контроля (мониторинг даты последнего скачивания файла).
- **Управление учётными данными SFTP.** При ротации ключей нужна координация с партнёром --- нет автоматического механизма обмена новыми ключами.
- **Формат файла --- ручная договорённость.** При изменении справочника ставок в АБС (новые поля, новые типы депозитов) нужна синхронизация с партнёром, иначе его система не сможет корректно разобрать файл.
- **SFTP-сервер --- единая точка отказа.** При его недоступности партнёр не получит обновление. Для MVP это приемлемо, для целевого состояния нужна кластеризация или резервный канал.
